# Repository Guidelines

## Project Structure & Module Organization

OpenBanners is a Vite React single-page app. Main application code lives in `src/`, with route-level and UI components in `src/components/`. Banner rerouting logic is grouped under `src/bannerRerouter/`, while shared helpers such as filters, SEO, constants, and sync state live directly in `src/`. Static assets and browser-facing files are in `public/`. Build and prerender tooling lives in `scripts/`; the TypeScript metadata fallback is in `server/banner-meta.mts` (tests in `server/banner-meta-tests.mts`). Project notes and manual regression material are in `docs/`.

Tests are colocated with the code they cover using `*.test.js` or `*.test.jsx`, for example `src/App.test.jsx` and `src/bannerRerouter/routeGenerator.test.js`.

## Build, Test, and Development Commands

Use Yarn 1, as pinned in `package.json`.

- `yarn install`: install dependencies from `yarn.lock`.
- `yarn dev` or `yarn start`: run the Vite development server for local debugging.
- `yarn test`: run Vitest once in jsdom.
- `yarn build`: create the production build in `dist/`.
- `yarn preview`: serve the built app locally for debugging a built bundle.
- `yarn prerender:banner <banner-id>`: generate static metadata HTML for a banner after a build.
- `docker compose -f docker-compose.public.yml up -d`: run the published GHCR image on local backend port `18080`; nginx exposes it publicly on the existing HTTPS port `443` using `docker/openbanners-nginx-container-location.conf` from the `openbanners.org` vhost. The included Watchtower service checks for new images and updates the container automatically.
- Do not deploy production by running `yarn build` locally or by restarting nginx for app code changes. After a completed change, commit and push to GitHub, wait for the Docker image workflow to publish `ghcr.io/gamer1120/openbanners:latest`, let Watchtower update the `openbanners-public` container, and then verify production at `https://openbanners.org/`.
- Always commit and push completed changes after verification; use the GitHub Docker image plus Watchtower path for production testing.
- The Docker image runs no PHP: it is based on `node:24-alpine`, and the build fails if a `php*` binary is present; nginx also returns 404 for `.php` URLs. `/banner/:id` metadata fallback is `server/banner-meta.mts`, run directly by Node (erasable TypeScript syntax only: no enums, namespaces or parameter properties; import local files with their `.mts` extension). Keep nginx routing for `/banner/` as prerendered static file first, then the metadata service on `127.0.0.1:8788`, then normal SPA behavior when it is unavailable. Run `node --test server/banner-meta-tests.mts` after changing it; the Docker build runs it too.

## Coding Style & Naming Conventions

Follow the existing JavaScript and JSX style: 2-space indentation, double quotes, semicolons, and ES module imports. React components use PascalCase file and function names, such as `BannerDetailsPage.jsx`; utilities use camelCase, such as `bannerFilters.js`. Keep component-specific styling near the component when practical, and avoid broad refactors when making targeted fixes in this stabilization-focused codebase.

There is no dedicated lint or format script in this repository. Match nearby code and run tests/builds before submitting changes.

## Continuous Learning

When a workflow, deployment step, testing note, or project-specific convention is discovered while working, add it to `AGENTS.md` in a concise, durable form so future agents can build on it.

Multiple agents may work in this repository at the same time. Before starting larger or risky work, check the current branch and worktree state, avoid overwriting unrelated changes, and prefer a separate `git worktree` for isolated parallel work when it would reduce coordination risk.

## Testing Guidelines

The test stack is Vitest, jsdom, and Testing Library, configured in `vite.config.mjs` with setup in `src/setupTests.js`. Add focused regression tests for route behavior, filtering, map interactions, rerouting logic, and API-state handling when those areas change. Mock external services and browser APIs in tests; the live app depends on Bannergress, OpenStreetMap, Google Fonts, Google Maps links, and Ingress links.

Local debugging with `yarn dev`, `yarn preview`, or focused tests is fine while developing. Always test changes on production as part of final verification after the GitHub Docker image workflow and Watchtower update have completed.

For `/map`, discovery banner loading should render each fetched page immediately; do not wait for every page in the viewport before plotting markers. Loaded discovery pages should remain cached in memory until the browser page is refreshed. The view in front of the user loads first (`src/discoveryMapData.js` page scheduler, 2026-10-29): the 3 request slots are taken per page, newest view first and centre tile first; tiles no view wants any more stop 400 ms after the view leaves them (open request aborted, queued pages dropped) and continue from their last page when needed again. Zoomed out, one tile can be hundreds of pages, so never go back to per-tile first-come-first-served slots.

The `/map` marker toggle supports image markers and Bannergress-style dots; dot colors should continue to reflect the effective Bannergress list state.

For `/map`, the banners in view (matching the filters) are cards sorted by distance from the map centre (`discoveryMap/BannerRow.jsx`, helpers in `rowModel.js`): on phones a freely scrolling row (no scroll snapping) above the bottom bar (swiping never moves the map; foldable, remembered in localStorage), on screens 840 px and wider a list on the right (hover lights the dot; `clamp(340px, 30vw, 440px)` wide) whose cards lead with the banner picture at full card width and its own aspect (whole up to 4 mission rows, taller ones pan), with a one-line title, then stats beside To do / Done / Hide icon toggles (the lit one replaces the status chip; Hide keeps the card until the page is left so it can be undone) and Details below it (2026-10-29, Michael: the pictures matter most, not the titles). Row cards (below 840 px; at most 376 px wide on phones, 440 px from 560 px viewports, half the row each from 784 px so two fit side by side; picture 100 px wide, 84 px on cards under 280 px, and on cards at least 340 px wide `clamp(132px, 100cqw - 230px, 160px)` up to the card's full inner height of 82 px, 2026-10-29 Michael: foldable pictures had too little width; 160 px is where a 6 × 3 banner fills the height) carry the same To do / Done / Hide toggles, shown only when the card itself is at least 340 px wide (`@container` on `.mv-rc-item`, e.g. a foldable's inner screen; 2026-10-29, Michael); narrower cards keep status chip + Details. jsdom has no container queries, so in tests the row toggles exist but are hidden (`getByRole(..., { hidden: true })`). Over 40 in view: the nearest 30 plus a "+N more · show list" card. Clusters that zooming can't split become the row. Selection is a tap toggle (2026-10-27, Michael): by default nothing is selected and no route is shown; tapping/clicking a card (or its dot) selects it (highlighted card, enlarged dot, route loaded at once), tapping it again (or empty map) deselects; the card's Details button opens the banner and never toggles. Never select anything automatically: not on scroll, re-sort, map move or a cluster becoming the row; desktop arrow keys only move focus. A selected banner that leaves the row (map moved, filters) is deselected. The phone row belongs to the finger: never re-sort or scroll it while a touch is down; it stays exactly where the momentum leaves it (no snap, no centring). The row scrolls itself only "nearest"-style to show a card selected via its dot or a half-hidden card, or after a re-sort (to the selected card, else back to the start); re-sorted cards apply only after it has been still for 400 ms.

Mouse-wheel zoom on every map is `src/mapWheelZoom.js` (imported by `src/index.jsx`; it replaces the methods of Leaflet's `ScrollWheelZoom` handler): one wheel notch = one zoom level, trackpad scrolling one level per 120 px, pinch (ctrl+wheel) counts 4×, steps during a zoom animation wait for it. Leaflet's default rounded every 40 ms burst up to a level (a short trackpad swipe zoomed ~10 levels). On `/map` the filter chip strip passes the pointer through except on the chips, it clears Leaflet's +/- buttons whenever they show (`.mv-root.zoomctl`), and zooming into a cluster fits it beside the desktop list (`SIDE_LIST_SPACE`).

Swiping right after a zoom is `src/mapZoomPress.js` (imported by `src/index.jsx`, every map; 2026-10-29, Michael: the map could not be moved for a split second after zooming): Leaflet ignores a whole drag or pinch that starts during its 0.25 s zoom animation (`L.Draggable._onDown` bails on `leaflet-zoom-anim`), so a press on the map (capture-phase `touchstart`/`mousedown`, not `pointerdown`, which would remove the touched tile before touchstart) first ends the animation with Leaflet's own `_onZoomTransitionEnd`. Touch drags also listen on the touched element, because right after a zoom it is often an old-level tile that Leaflet prunes mid-swipe and touch events on a removed element no longer reach `document`. Headless check: CDP `Input.dispatchTouchEvent` pinch, then a one-finger drag 0-900 ms later at 760x900 with 4x CPU throttle; the map pane's translate3d must move.

In `/map` dot marker mode, overlapping banners should cluster into numbered dots instead of being displaced with connector lines.

When a `/map` dot marker cluster opens the disambiguation picker, render the choices as list-colored dots rather than banner thumbnails.

Mixed `/map` dot marker clusters should use segmented colors for the represented list states, and single dot markers should expose the banner title on hover.

For `/map`, list-state filters such as to-do-only and show-done depend on Bannergress list metadata and should remain mutually exclusive with Show hidden banners.

Banner Together creates live peer rooms under `/together/:placeId/live/:roomId`. Keep the room secret in the invite fragment and keep Bannergress tokens out of every room request. Todo, Done, and Hide snapshots must travel only as end-to-end encrypted WebRTC data-channel messages after each participant explicitly enables sharing. The v3 signaling service may hold only bounded room verifiers, hashed participant tokens, presence, and native SDP/ICE messages in memory; it must not accept application payloads, write room state to disk, or use a database. Rooms support at most eight peers, expire after four hours, and disappear when no peers remain. Cache private membership snapshots only in the browser, scoped to the authenticated account and place, for less than four hours; show the snapshot age and keep a manual refresh action. `/api/` and retired Banner Together API versions must return 404. Legacy `#banner-together=` snapshot links remain read-only until their normal expiry.

Banner Together offline sharing is a separate, default-off opt-in that is available only while **Share my lists** is enabled. Encode that preference inside the encrypted peer snapshot; peers may retain an opted-in snapshot in browser memory after disconnect, but the signaling service must never store it.

On `/together/` routes, do not run the TopMenu full-account list auto-sync; the route owns its place-scoped membership and catalog caches. Bannergress `/bnrs` pages are capped at 100. Banner Together should probe the first page and then use bounded four-request windows, and it must classify singular private-list requests by the requested list because `BannerDto.listType` is optional.

Banner pictures (`banner.picture`) are rendered only through `src/components/BannerImage.jsx`, which owns the tall-banner pan (Bannergress's 8 s loop: 5 s down / 1 s pause / 1 s up / 1 s pause, 2026-10-29 Michael; also under reduced motion, no pan below 3 % or 12 px overflow). `src/bannerImageGuard.test.js` fails if a component renders the picture itself. Mission pictures are not affected.

## Translation editor

`/translate` (More menu → "Translation editor"; `src/components/TranslationEditor.jsx`, lazy-loaded with `keys.json`) lists every UI text of one language (default: the UI language; English is not editable) next to the English, with search and All / Not translated / Your suggestions filters; plural keys show each `Intl.PluralRules` form of the language separately. Suggesting needs the Bannergress login. The passphrase service handles it (`server/translations.mjs`, tests `server/translations-tests.mjs`): `GET /translations/:lang/approved` (public), `GET /translations/:lang/mine` and `POST /translations/:lang/suggestions` (`{ key, form, text }`; login; same `{placeholders}` as the English, no `<>` markup, at most 4× the English + 40 characters, 200 a day per account except `OPENBANNERS_UNLIMITED_AGENTS`). It checks keys against `keys.json` and the bundled locales: from `server/i18n/` in the Docker image (copied by the Dockerfile; `.dockerignore` lets `src/i18n/keys.json` and `locales/` in), from `../src/i18n` on test. Tables `translation_suggestions`, `translation_overrides`, `translation_reviews` live in the same SQLite file, so the nightly backup covers them. The passphrase bot moderates them (`server/translations-telegram.mjs`): one message per language once nobody has suggested anything for that language for the quiet period (split when long), showing key, English, current, suggestion and agent, with Approve / Reject per suggestion and Approve all / Reject all (callback data `tr:…`); /pending re-sends them. Approved suggestions are live at once: `src/i18n/index.js` fetches the language's approved overrides (waiting at most 0.8 s, cached in localStorage) and merges them over the bundled locale. `node scripts/i18n-apply-overrides.mjs [--url https://test.openbanners.org | --db path] [--dry-run]` writes them into `src/i18n/locales/*.json` for a commit.

## Installable app (PWA)

The Android WebView APK (`public/OpenBanners.apk`) was retired on 2026-10-27; nginx redirects `/OpenBanners.apk` to `/`. The site itself is the app: `public/manifest.json` (id/start_url/scope `/`, standalone, dark `#16161c`, 192/512 icons plus `maskable-512.png`) and `public/sw.js`. The More menu's "Install app" (`src/pwaInstall.js`, `InstallAppDialog.jsx`) calls the saved `beforeinstallprompt` on Chromium, shows Share → Add to Home Screen on iOS, tells old WebView-app users to open the site in Chrome, gives browser-menu hints elsewhere, and is hidden when running installed. `src/pwaInstall.js` is imported by `src/index.jsx` so the event isn't missed, and registers the service worker in production builds only. Service worker rules: it caches nothing; it only answers same-origin GET navigations (network, with an inline offline page when that fails) and never calls `respondWith` for anything else — never for `/bannergress-auth-callback.html`, `/_openbanners/`, `/api/`, cross-origin (Bannergress API/login) or assets. Don't add caching of `index.html` or API traffic. `docker/nginx.conf` serves `/sw.js` and `/manifest.json` with `no-cache` and 404 (not the SPA shell) when missing.

The More menu's "Download OpenBanners Overlay" (`OverlayDownloadDialog.jsx`, links in `OVERLAY_LINKS`) lists Google Play first (closed test: join the Google Group `openbanners-overlay`, wait ~2 minutes, then the `play.google.com/apps/testing/org.openbanners.overlay` opt-in page), then F-Droid, then the latest GitHub release of Gamer1120/OpenBanners-overlay. When the app leaves testing on Play, replace the steps with the store link.

"Start with Overlay" (banner page) and "Start in OpenBanners Overlay" (planner) use Android intent URLs (`src/overlayLink.js`) whose `S.browser_fallback_url` is the same page on the current origin with `?overlay=missing` (Chrome can't tell a page whether an app is installed; it opens the fallback when the package is missing). That page then shows `OverlayMissingDialog` (same download options as the More-menu dialog) and removes the parameter with a replace navigation so reload/back don't reopen it. On the banner page the dialog adds "Open in Bannergress Overlay": `navigator.share` with `https://bannergress.com/banner/<id>` (clipboard copy where sharing isn't available). Off Android, "Start with Overlay" opens the dialog straight away. In in-app browsers (`detectInAppBrowser`, e.g. Telegram's WebView, which may ignore `intent://`) it opens the dialog first, titled "Start with OpenBanners Overlay", with a "Start with Overlay" button that fires the plain `openbanners-overlay://` link, "Open in browser" (intent to the default browser) and the install options. Anywhere on Android, `watchAppLaunch` (`overlayLink.js`) shows the dialog ("didn't open") when the page is still in front 1.5 s after the link; the page going hidden, `blur` or `pagehide` cancels it, so it never shows when the app opened. The planner's button does the same. Not verified in a real Telegram app (2026-10-30).

Signed out, the top bar shows a labelled filled "Sign in" button (login icon + `t("Sign in")`, title "Sign in with Bannergress"; also the first More-menu item) instead of a bare icon (`TopMenu.jsx`, 2026-10-30 Michael: people didn't recognise the icon as sign-in); signed in, the avatar. Keep the label in every language on a 360 px phone (all 15 fit, the longest is about 130 px). To do / Done / Hide toggles (banner page, Browse list rows, map cards) check `isSignedInToBannergress()` first and say "Sign in to use To do, Done and Hide." (the banner page adds a Sign in button) instead of sending a request that can only 401. The sign-in UI only renders on supported https origins, so to screenshot a local build, load https://openbanners.org in headless Chrome with CDP `Fetch` interception serving `vite preview` (pass `/_openbanners/` through) plus `Network.setBypassServiceWorker` and cache disabled.

Bannergress sign-in from the installed app opens in a Chrome custom tab where `window.opener`/`window.name` can be lost, so `public/bannergress-auth-callback.html` must find the PKCE data in localStorage under `BANNERGRESS_AUTH_PENDING_STORAGE_KEY` (`openbanners:bannergress-auth-pending`, the old dash name is accepted too); `src/bannergressAuthCallback.test.js` runs the page's script to keep the two in step.

## Join on Telegram

More menu → "Join on Telegram" (`src/components/TelegramJoinDialog.jsx`, client `src/telegramJoin.js`) gives Bannergress users invite links to the OpenBanners Telegram channel and group through @OpenBannersBot. Server and bot are one process, `server/telegram-join.mjs` (no dependencies; tests `node --test server/telegram-join-tests.mjs`, also run by the Docker build), port 8791 behind `docker/nginx.conf` `/_openbanners/telegram/v1/` (no body, no access log). `GET /status` → `{ enabled, bot }`; `POST /code` needs `Authorization: Bearer <Bannergress token>` (401 without; 503 `not_configured` until chats are set; 403 `not_verified` without a verified agent), checked once with Bannergress `GET /user` and returns a 192-bit base64url one-time code plus `https://t.me/<bot>?start=<code>`. The dialog fetches the code when it opens so the button is a real link (no popup blocking on phones) and gets a new one after 9 minutes or on "Get a new link". The bot takes `/start <code>` in private chats only, marks it used and sends one `createChatInviteLink` per chat with `member_limit: 1` and `expire_date` now + 15 min (if no link can be made the code stays usable); bad/expired/used codes and plain messages get pointed to openbanners.org.

Privacy rules (Michael's requirements, keep them): never store or log the Bannergress token or agent name, nor any Telegram user id/name; the server keeps only sha256(code), expiry (10 min) and a used flag, in memory (lost on restart, which is fine); nothing links a code to an account; no per-day limit (only a 20,000-code memory cap and the nginx rate limit). The only use of a user id is comparing the sender to `OPENBANNERS_JOIN_ADMIN_IDS`.

Settings (`env_file: /etc/openbanners/telegram-join-prod.env`, root 600 on the VPS, added to the `web` service in `/var/www/OpenBanners/docker-compose.public.yml`): `OPENBANNERS_JOIN_BOT_TOKEN` (@OpenBannersBot; never print it), `OPENBANNERS_JOIN_ADMIN_IDS` (Michael: 164274953), `OPENBANNERS_JOIN_CHATS` (chat ids, comma-separated: announcement channel first, then the discussion group), optional `OPENBANNERS_JOIN_CHAT_LABELS` (button labels, same order; default "OpenBanners announcements", "OpenBanners chat"). Without chats the feature is off and the dialog says "not available yet". Only one process may poll the token, so there is no test instance. Setup: an admin listed in `OPENBANNERS_JOIN_ADMIN_IDS` first sends the bot any message (so it may DM them), then adds it as admin with "Invite users via link" to the channel and the group (private group, "Join to send messages" on); the bot DMs the chat title, id and whether it may invite. Append `OPENBANNERS_JOIN_CHATS=<channel id>,<group id>` to the env file (back it up first) and `docker compose -f /var/www/OpenBanners/docker-compose.public.yml up -d web`. An admin's `/status` to the bot checks the configured chats. Startup log lines: `telegram-join: bot @OpenBannersBot polling` and `OpenBanners Telegram join listening on 127.0.0.1:8791 (not configured | N chats)`.

## Commit & Pull Request Guidelines

Recent history uses short imperative commits, with occasional conventional scope prefixes such as `fix(bannerguider): don't open new missions on blank`. Prefer concise subject lines that describe the behavior change, for example `Fix browse pagination after filters`.

Pull requests should include a summary, testing performed (`yarn test`, `yarn build`, manual route checks), linked issues when applicable, and screenshots or screen recordings for visible UI changes. Mention changes that affect deployment, prerendering, or external API assumptions.

## Security & Configuration Tips

Do not commit secrets, local tokens, or production certificate material. Treat `server/banner-meta.mts`, prerendered metadata, Docker deployment files, nginx proxy snippets, and third-party API contracts as deployment-sensitive paths; verify them through the GitHub Docker image workflow and live production smoke checks when touched.

The app shell, Home, Browse, Search, Lists and the banner page follow prototype "X" (2026-10-20): Material 3 tokens in `src/m3.css` (light/dark via `data-theme` on `<html>`, set by `src/themeMode.js`; the theme choice lives in the top bar's More menu). ## Passphrase answers

`server/passphrases.mjs` (node:sqlite, no dependencies; tests `node --test server/passphrases-tests.mjs`) serves `/_openbanners/passphrases/v1/`. Reading is public; submitting, voting and author actions send the Bannergress access token, which the server checks with Bannergress `GET /user` and never stores or logs. Authors are only the *verified* agent from `/user` (`agent.name`), matched to mission authors from an authenticated `/bnrs/:id`; `preferred_username` is not proof. "Mission number" answers go live once a moderator approves them, other answers need a moderator too and wait 30 days unless an author approves sooner; each account may add 500 answers a day, except the verified agent names in `OPENBANNERS_UNLIMITED_AGENTS` (comma-separated); an author objection (one banner or all their banners) deletes the answers permanently and blocks new ones. Typed crowd answers also need a moderator's approval: `server/passphrases-telegram.mjs` (started by the service when `OPENBANNERS_TELEGRAM_BOT_TOKEN` is set; moderators are the Telegram user ids in `OPENBANNERS_TELEGRAM_MODERATORS`) sends one message per banner, once nobody has added answers to it for 15 minutes (`OPENBANNERS_TELEGRAM_QUIET_MINUTES`), with Approve all (still waits the 30 days) / Publish all now / Reject all and a Per answer view; it has /pending, /blocks, /block, /unblock and /contact. Other people writing to the bot get the how-to-object text and are forwarded to the moderators. Only one service may poll a bot token, so test and production need different bots. `server/passphrases-admin.mjs` lists pending answers with authors and contact attempts, and applies objections that arrive outside the site (e.g. Telegram).

On test it runs as `openbanners-passphrases-test.service` (user `openbanners`, port 8790, DB `/var/lib/openbanners-passphrases-test/passphrases.sqlite`, bot token (@TestOpenBannersPassphraseBot) and moderators in the root-only `/etc/openbanners/passphrases-test.env`; the production bot @OpenBannersPassphraseBot is waiting in `/etc/openbanners/passphrases-prod.env`); the test deploy script restarts it, the test nginx vhost proxies the path, and `/usr/local/sbin/vps-backup-run` copies every `/var/lib/openbanners-passphrases-*/passphrases.sqlite` into the nightly restic backup. In production the Docker entrypoint runs it on port 8789 behind `docker/nginx.conf`, with the DB on the `/data` volume (host `/var/lib/openbanners-passphrases-prod`, owned by uid 1000) and the bot settings from `env_file: /etc/openbanners/passphrases-prod.env` (@OpenBannersPassphraseBot); the VPS compose file `/var/www/OpenBanners/docker-compose.public.yml` has the same volume and env_file. The Docker build runs the passphrase tests.

Personal banner notes (`src/bannerNotes.js`, `src/components/bannerDetails/BannerNotes.jsx`) show on the banner page only while logged in. The passphrase service keeps them in plain text per Bannergress account (`banner_notes` table, `GET`/`POST /notes/banners/:id`, at most 10,000 characters per note); every request needs the login, and an account only ever gets its own notes. Saving an empty note deletes it.

The Mission Day planner (`/planner`, `/planner/:planId`; `src/missionPlans.js`, `src/components/MissionDayPlanner.jsx`; More menu → "Mission Day planner") features Bannergress's active Mission Days (the same query as Bannergress's home page: `minEventTimestamp` = `maxEventTimestamp` = now, `online`, newest first) and a banner search. Picking a banner creates a plan (needs a Bannergress login, at most 200 per account) in the passphrase service's `plans` table; the random 22-character id in the link is the only key, and anyone with it can view and edit without logging in. Each plan also has a read-only link (`view_id`, Share → "Read-only link"): the server answers it with `readOnly: true` under the view id and never reveals the edit id, refuses edits through it (403 `read_only`), and the page hides every editing control. Edits are small operations (`title`, `addBanner`, `removeBanner`, `add`, `remove`, `move`, `done`) applied server-side in one transaction, so simultaneous editors don't overwrite each other; the page applies them locally at once (`applyOps`, keep it in step with the server) and polls every 10 s. Plans hold at most 30 banners and 500 missions. The plan page has a map (`PlanMap.jsx`) drawn like the banner page's: every mission's route and portals in its rainbow colour (`missionColors`, by number in its banner) with the numbered start marker; planned missions are bold rainbow lines with a white edge, portal dots and bigger starts numbered by your order (done ones dimmed); the others are thin grey lines with small grey starts showing their banner number (tap a start to add or take out), dashed walks between planned missions, and "Near me", which follows your location and sorts the mission chips nearest first. "Start in OpenBanners Overlay" (Android) opens `openbanners-overlay://plan/{id}?start=1&origin=…` (overlay v42+), and the overlay also accepts a shared `/planner/{id}` link: it follows the plan's missions that aren't done as one route and marks each one done in the plan when you go on from it. Every planned mission also links to Ingress.

Link previews: nginx sends every page load that isn't a file to `server/banner-meta.mts`, which fills the SPA shell's title, description, `og:*`/`twitter:*` tags and canonical URL from the route table in `server/page-meta.mjs` (looking up banners, places and Mission Day plans where a page has `kind`; falling back to the page's own text). Every `<Route path>` in `src/App.jsx` must have an entry in `PAGES` — `src/pageMeta.test.js` fails otherwise. Every page gets a large preview image (`summary_large_image`): banners their Bannergress picture and Mission Day plans their first banner's picture; every other page (and a banner or plan without a picture, and the static `index.html` shell) gets the site's own 1200×630 card `public/og-image.png` (`DEFAULT_IMAGE` in `server/page-meta.mjs`, with `og:image:width`/`height`/`alt`; 2026-10-30, Michael asked for it before the Telegram launch post: logo, name, tagline and a banner grid, made from `docs/og-image-source.html` with headless Chrome at 1200×630). Never use `logo512.png` as a preview (old Telegram previews still show the React logo it once was). A path no route matches gets the plain shell with status 404 and `noindex`; the app shows "Page not found" (App.jsx `path="*"`, `NotFoundPage.jsx`), and `src/components/ErrorBoundary.jsx` (around the whole app and around Home's `<main>`, reset on navigation) replaces a white screen after a render crash. `matchPage` is case-insensitive like React Router. A banner Bannergress answers 404 (or 410) for gets status 404 + `noindex` + "Banner not found" from the meta service (remembered 5 min, `MISSING_TTL_MS`); the banner page then says "This banner doesn’t exist (any more) on Bannergress." with Search / Map links and no Retry. Network errors, timeouts (20 s) and other non-OK answers say "Bannergress, where the banner data comes from, isn’t responding right now. Try again in a minute." with Retry (`bannerResponseProblem` in `bannerDetails/shared.jsx`).

## First visits (2026-10-30, before the Telegram launch post)

- Sign-in in in-app browsers: Google blocks its sign-in in embedded WebViews and Bannergress signs in only with Google. `src/inAppBrowser.js` recognises Telegram (UA or `TelegramWebviewProxy`), Instagram, Facebook, Messenger, Discord, WhatsApp, LINE, Snapchat, TikTok, Android `; wv)` and iOS WebKit without `Safari/` (not the old `OpenBannersApp` WebView, which signs in via a custom tab, and not an installed iOS web app). There the sign-in button (and every `BANNERGRESS_AUTH_REQUEST_EVENT`) opens `InAppBrowserDialog` instead: why, "Open in browser" (Android: an `intent://…#Intent;scheme=https;action=VIEW;category=BROWSABLE;end` link without package, so the default browser), the ⋮ / ⋯ → "Open in Safari" hint, "Copy link", and "Try signing in here anyway". Not verified in a real Telegram app.
- When `window.open` returns null (popup blocked), the sign-in runs in the same tab: the pending PKCE data carries `mode: "redirect"` and `returnTo` (a same-site path), and `bannergress-auth-callback.html` goes back there after the token exchange. The callback page always has a "Back to OpenBanners" link to `returnTo`.
- Home shows `FirstVisitIntro` (two lines + Map / Mission Day planner / Overlay links) until it's closed (`openbanners:intro-dismissed`) and never to people with signs of earlier use (Bannergress login, saved map state, saved home city).
- `/map` without a saved view starts on a world view (`src/mapDefaults.js`: zoom 2, 3 on very tall screens, centred on the visitor's region from the browser time zone) instead of Enschede; other maps use the world as their pre-fit placeholder. Views whose tiles would be above `MIN_LOAD_TILE_LEVEL` (6: 5.6° tiles, about zoom 6 on a phone / 7 on a desktop) fetch nothing from Bannergress and say "Zoom in to see banners" (they still show banners already loaded): a level-6 tile over the Netherlands is 3,000–6,000 banners, a world tile tens of thousands.
